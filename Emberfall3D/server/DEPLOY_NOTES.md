# Online room service

`rooms.mjs` exports `makeRoomService({store, now?, random?})`, `D1RoomStore`, `MemoryRoomStore`, and `RoomError`. The service has `create(input,address?)`, `join(code,input,address?)`, `get(code,token)`, `start(code,token)`, `action(code,token,{seq,action})`, `leave(code,token)`, and `fetch(Request)`. The direct methods return snapshots or throw `RoomError`; `fetch` returns JSON HTTP responses.

Worker integration: import `D1RoomStore` and `makeRoomService`, construct the service from `new D1RoomStore(env.DB)`, and delegate `/api/` requests to `service.fetch(request)`. Reuse a service per binding/isolate when possible. There is no in-memory fallback for hosted storage. `game-core.js` must attach its UMD export to `globalThis.BattleCore` even in Node. Bundle the core before the service in the deployment Worker.

Sites requirements (read from installed Sites 1.1.1 storage reference, Worker starter and packaging helper): preserve project identity/audience; set `.openai/hosting.json` `d1` to the logical string `"DB"`, leave unused `r2` null, omit `static` for Worker ESM. Keep the existing starter build integration. Worker entry must be `dist/server/index.js` with default `{fetch}`. Source migration directory is `drizzle/`; `package-site.mjs` copies it to `dist/.openai/drizzle`. Include SQL, metadata snapshot and journal in source. Sites applies hosted migrations before Worker upload. Local preview storage is separate. Migration 0000 contains only CREATE TABLE/INDEX, never records or backfills. Request handling never executes DDL. Do not rewrite applied migrations; append new ones.

Each room is one versioned D1 record. Every state change uses `UPDATE ... WHERE code=? AND version=?` and retries from persisted state on contention. No client snapshot or arbitrary state fields are accepted. Credentials use 256-bit cryptographic tokens; only SHA-256 digests persist. Room codes use cryptographic bytes and a unique primary key. The token belongs to one player in one room; it is never returned in state snapshots or URLs.

Poll every 250 ms. Serialize client action requests and increase `seq` monotonically; `ackSeq` is returned. Replayed/stale sequences do not apply twice. Syntactically valid commands rejected by the game (cooldown, gold, etc.) consume sequence and return `actionResult`. GET/start/action responses include authoritative state, server time, room version and connection status. Time advances in fixed 0.05s steps, at most 2s per request. After 15s without polling, a disconnected hero is bot-controlled; a new authorized request restores player control. Explicit leave invalidates its token. Host passes to the next player. Joining after match start is disabled.

Lobby expires after 30 minutes idle; playing rooms after 15 minutes; finished rooms after 5 minutes. Expiry is enforced on access; creation opportunistically cleans at most 32 expired rows. Body limit: 4096 bytes. Durable player limit: 30 requests/s with burst45; actions20/s with burst25. Best-effort per-isolate entrance limits: create8/minute and join30/minute. Production edge/IP limits may be added independently; local throttle is not a distributed global quota.

`node server/node-server.mjs --port 4173` explicitly starts the dependency-free local HTTP adapter with in-memory room persistence. It serves `public/` only and does not start on import. `node --test tests/rooms.test.mjs` starts ephemeral loopback listeners inside tests and closes them. In-memory rooms disappear on process exit. Hosted rooms require the D1 migration and configured binding; successful local tests are not proof that hosted deployment/migration completed.

The CLI binds only to `127.0.0.1` by default. Explicit LAN use: `node server/node-server.mjs --host 0.0.0.0 --port 4173`, then open `http://<computer-LAN-IP>:4173` from another device on the same network. The OS firewall must allow the chosen port. The development adapter uses HTTP and bearer credentials; use it only on a trusted local network. It is not a public production server. Actual two-device LAN access is not established by loopback tests.

Verification: 11 test groups passed on Node 24.19.0. Tests execute the schema SQL and D1 adapter against the real built-in SQLite engine, and two independent HTTP clients reach separate room services that share this database. They verify shared movement, spell damage through shields and into HP, identical observed state, host authorization, room isolation, body/JSON validation, replay protection, CAS retries, team capacity, bots, expiry and rate limits. Test listeners are closed afterward. The SQLite tests require Node 22.13+; a real hosted D1 deployment remains a separate verification step.
